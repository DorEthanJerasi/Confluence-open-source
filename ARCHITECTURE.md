# Stillwater — Architecture

Stillwater is a self-hosted team wiki: spaces, nested pages, a block editor,
search, page history and AI help, with a calm, soft look in light and dark mode.

This file records the decisions that are expensive to undo. Change them only
through the team lead. Everything not fixed here is the builder's call.

---

## 1. Name and originality

- The product name is **Stillwater**. Package scope is `@stillwater/*`.
  Database, cookie, env and container names use `stillwater` / `STILLWATER_`.
- Stillwater works like the established wiki tools, but the name, words, look,
  icons, colours and code are our own. No other company's product names, logos,
  icons, colours, fonts, copy or code are used anywhere in the repo.
- `node scripts/check-original.mjs` enforces this. It fails on banned product or
  company names, their design-kit packages, and their signature brand colours,
  in file contents and file names. It runs in `npm run check` and in CI.
  The only files it skips are the owner's brief (`PROJECT.md`), the agent
  folder (`.claude/`) and generated output (`node_modules`, `dist`, lockfiles…).

## 2. Repository layout — TypeScript monorepo

npm workspaces, Node 22, TypeScript `strict` everywhere, ES modules.

```
apps/
  server/        Fastify API, Drizzle schema + migrations, auth, search, AI, file storage
  web/           React + Vite single-page app (Tiptap editor, routing, UI)
packages/
  shared/        zod schemas and TS types used by both sides (API contracts, roles)
  editor-schema/ the Tiptap extension list = THE document schema (used by web AND server)
e2e/             Playwright tests (run against the docker compose stack)
scripts/         check-original.mjs, smoke.sh, dev helpers
docker/          Dockerfile, entrypoint
docker-compose.yml, .env.example, install.sh, INSTALL.md, ARCHITECTURE.md
```

- In production the server serves the built web app as static files, so the
  whole product is **one container + Postgres**.
- Root scripts (the contract every role relies on):
  - `npm run dev` — Postgres from compose + server and web in watch mode
  - `npm run build` — builds all workspaces
  - `npm run check` — typecheck, lint, unit/integration tests, `check-original`
  - `npm run e2e` — Playwright against a running stack (AI on the stub)

## 3. Editor and document model (Yjs-ready)

**Editor:** Tiptap 2 on ProseMirror, in `apps/web`.

**One schema, shared.** `packages/editor-schema` exports `getExtensions()`, the
single list of Tiptap nodes and marks. The web editor, the server-side text
extractor and (later) the co-editing server all import it. A node type that is
not in this package does not exist.

**Stored shape.** A page body is ProseMirror JSON (`editor.getJSON()`), stored in
`pages.doc` as `jsonb`. Rules that keep it ready for Yjs:

1. **Schema-only content.** The document holds only what the schema defines:
   node types, attrs and marks. No UI state, no computed values, no HTML strings.
2. **Every top-level block has a stable `id` attr** (UUID, added by a global
   attribute extension, kept on copy-split by regenerating). Used for history
   diffs, deep links and comments later; Yjs keeps attrs as-is.
3. **Embeds are references, never blobs.** Images, files and video store an
   `attachmentId` (or an allow-listed external URL) in attrs. No base64 in the
   document. Link previews store the URL; the preview card data lives in the
   `link_previews` table and is fetched on render.
4. **Tiptap's own History extension stays separate** from document storage
   (`StarterKit.configure({ history })`), so it can be swapped for the Yjs undo
   manager by flipping one flag.
5. **Saving goes through one function**, `savePage(pageId, doc, baseVersion)`,
   on both sides. Today the client autosaves (debounced ~1 s) the full JSON with
   the version it started from; the server rejects a stale `baseVersion` with
   409 and the client offers reload. Nothing else writes `pages.doc`.

**How co-editing is added later, without a rewrite:**
add `@tiptap/extension-collaboration` + `y-prosemirror` on the client, a
Hocuspocus-style WebSocket endpoint on the server that loads/saves a Y.Doc into
the reserved nullable column `pages.ydoc_state bytea`, and have that server call
the same `savePage` (JSON derived from the Y.Doc via `TiptapTransformer`) on a
debounce, so search, history and AI keep working unchanged. The schema package,
the JSON column and the history table do not change.

**Blocks we ship:** paragraph, headings 1–3, bullet/numbered/task lists,
quote, divider, callout, code block (syntax highlight via lowlight), table,
image, file, video (upload or allow-listed YouTube/Vimeo), link preview card,
mention of a page. All reachable from a `/` slash menu and from Markdown
shortcuts.

## 4. Storage — Postgres + Drizzle

- Postgres 16, run by `docker-compose.yml`. Single `DATABASE_URL`.
- Drizzle ORM; schema in `apps/server/src/db/schema.ts`; SQL migrations
  generated by `drizzle-kit generate` into `apps/server/drizzle/` and committed.
  **Migrations run automatically on server start** (`migrate()` before listen).
  Never edit an applied migration; add a new one.
- IDs are UUIDs (`gen_random_uuid()`). Timestamps are `timestamptz`.

Core tables:

| table | key columns |
|---|---|
| `users` | id, email (unique, lower-cased), name, password_hash, role (`admin`/`editor`/`viewer`), created_at, disabled_at |
| `sessions` | id, user_id, token_hash (sha256), expires_at, created_at, last_seen_at |
| `spaces` | id, key (short slug, unique), name, description, visibility (`open`/`restricted`), default_role, created_by |
| `space_members` | space_id, user_id, role (`admin`/`editor`/`viewer`) — PK (space_id, user_id) |
| `pages` | id, space_id, parent_id (nullable, same space), position (fractional-index text), title, doc jsonb, doc_text text, search tsvector (generated), version int, ydoc_state bytea null, created_by, updated_by, created_at, updated_at, deleted_at |
| `page_versions` | id, page_id, version, title, doc jsonb, author_id, created_at, saved_at, restored_from (nullable) |
| `attachments` | id, space_id, page_id, filename, mime, size, storage_key, created_by, created_at |
| `link_previews` | url (PK), title, description, image_url, site_name, fetched_at |

- **Page tree:** adjacency list (`parent_id`) + `position` fractional index for
  ordering siblings. Moves check for cycles. Breadcrumbs and subtree queries use
  recursive CTEs. Delete is soft (`deleted_at`) and cascades to children.
- **Files:** a `FileStorage` interface (`put`, `get`, `delete`). Default is local
  disk at `/data/uploads` on a named volume; S3-compatible can be added later.
  Files are served only through an authenticated route that checks the
  attachment's space permission. Size limit `MAX_UPLOAD_MB` (default 25).
- **Link previews:** server-side fetch of Open Graph tags, 5 s timeout, 1 MB cap,
  refuses private/loopback/link-local addresses (SSRF guard), cached in
  `link_previews`.

## 5. Page history

- Every save bumps `pages.version`. A row is written to `page_versions` when the
  author changes or the last snapshot is older than 5 minutes; otherwise the
  latest snapshot by the same author is updated in place. So history is
  readable, not one row per keystroke.
- **Restore never deletes.** Restoring version N writes its title and doc as a
  new current version (with `restored_from = N`) through `savePage`. Every
  earlier version stays restorable.
- The history view shows author, time and a block-level diff (using block ids).

## 6. Search — Postgres full-text

- On every save the server walks the doc with `packages/editor-schema` and
  writes plain text to `pages.doc_text`.
- `pages.search` is a generated column:
  `setweight(to_tsvector('english', title), 'A') || setweight(to_tsvector('english', doc_text), 'B')`
  with a GIN index. Queries use `websearch_to_tsquery('english', q)`, ranked by
  `ts_rank_cd`, snippets by `ts_headline`. Title prefix matches are added for
  the quick-find box.
- **Permission filter is part of the SQL**, via the one shared helper
  `visibleSpaceIds(user)` (see §7). Search never returns a page the user cannot
  open, and deleted pages are excluded.

## 7. Auth, roles and space permissions

- **Accounts:** email + password. Passwords hashed with argon2id
  (`@node-rs/argon2`), library defaults (19 MiB, t=2, p=1). Login is
  rate-limited per IP and per email. The e2e stack alone sets
  `E2E_FAST_PASSWORD_HASH=1` on its throwaway servers for a cheap hash
  (`e2e/global-setup.ts`); compose, `.env.example` and the Dockerfile never
  set it, and `apps/server/test/password.test.ts` checks both.
- **Sessions:** server-side, in Postgres. The browser holds an opaque random
  token in an `httpOnly`, `SameSite=Lax`, `Secure`-when-HTTPS cookie
  (`stillwater_session`); only its sha256 is stored. 30-day sliding expiry.
  Logout deletes the row.
- **CSRF:** `SameSite=Lax` plus an `Origin` check on every non-GET request.
- **Sign-up:** the first account becomes instance **admin**. After that sign-up
  is open (new users are `editor`) unless `ALLOW_SIGNUP=false`, in which case
  admins invite/create users.

**Roles.** Two levels, one rule.

- Instance role on the user: `admin` (manages users and every space),
  `editor` (may create spaces), `viewer` (read-only everywhere).
- Space role, per space: `admin` (settings, members, delete), `editor`
  (create/edit/move/delete pages, upload), `viewer` (read, search, AI on what
  they can read).
- A space is `open` (every signed-in user gets the space's `default_role`,
  usually viewer) or `restricted` (members only). The creator becomes space admin.

**Effective role** in a space, computed in exactly one place,
`apps/server/src/auth/permissions.ts`:

```
if user.role == admin            -> space admin
base = membership.role ?? (space.visibility == open ? space.default_role : none)
if user.role == viewer           -> min(base, viewer)
else                             -> base
```

Every route calls `requireSpaceRole(user, spaceId, needed)`. List, search, AI
retrieval and file download all use the same `visibleSpaceIds(user)` SQL
helper, so there is no second permission path to drift.

## 8. AI — provider interface, Anthropic default, test stub

```ts
// apps/server/src/ai/provider.ts
export interface AiProvider {
  readonly name: string;
  complete(req: {
    system: string;
    messages: { role: 'user' | 'assistant'; content: string }[];
    maxTokens: number;
  }): Promise<{ text: string }>;
}
```

- **`AnthropicProvider`** — official `@anthropic-ai/sdk`, key from
  `ANTHROPIC_API_KEY`, model from `AI_MODEL` (default `claude-opus-5-5`; hosts
  may set `claude-sonnet-5-5` or `claude-haiku-5-5` to cut cost).
- **`StubProvider`** — deterministic, no network. Summaries are built from the
  first sentences of the input; answers quote the first source and cite it.
  Used by all automated tests, so tests cost nothing.
- **Selection** (`AI_PROVIDER`): `anthropic` | `stub` | `off`. If unset:
  `anthropic` when `ANTHROPIC_API_KEY` is set, otherwise `off`.
  `GET /api/ai/status` returns `{ enabled }`; when off, the UI hides every AI
  control. The key never reaches the browser.

**Features built on the interface** (in `apps/server/src/ai/features.ts`, not in
the provider):

- **Summarise page** — page text (truncated to a token budget) → short summary.
  Requires viewer on the page's space.
- **Ask your docs** — question → full-text search over the asker's
  `visibleSpaceIds` → top pages split into chunks by heading, best 8 chunks sent
  as numbered sources → the model must answer only from them and cite `[n]` →
  the server maps each `[n]` to `{ pageId, title, url }` and drops citations it
  did not supply. Answer with no usable sources says so plainly.
- Prompts live in one file, `apps/server/src/ai/prompts.ts`. Page text is
  wrapped as data, never as instructions.

## 9. Web app and look

- React + Vite + React Router + TanStack Query. API calls go through one typed
  client built on the `packages/shared` zod contracts.
- Design tokens (colour, spacing, radius, type, shadow, motion) are CSS custom
  properties in `apps/web/src/styles/tokens.css`, owned by the designer.
  Light and dark via `data-theme` on `<html>`, defaulting to the system setting,
  user choice remembered. Motion is short and eased and turns off under
  `prefers-reduced-motion`. Text meets WCAG AA contrast in both themes.
- Icons: an open-licence set (Lucide) or our own; no third-party brand icons.

## 10. Self-hosting

- `docker compose up` starts `app` (our image) and `db` (`postgres:16-alpine`)
  with named volumes for data and uploads, health-checked; the app waits for
  the DB, runs migrations, then serves on `PORT` (default 3000).
- All config is env, documented in `.env.example`: `DATABASE_URL`,
  `SESSION_SECRET`, `PUBLIC_URL`, `ALLOW_SIGNUP`, `MAX_UPLOAD_MB`,
  `AI_PROVIDER`, `ANTHROPIC_API_KEY`, `AI_MODEL`.
- `install.sh` installs and starts the site in the foreground on `$PORT`;
  `INSTALL.md` gives the plain steps, plus backup/restore (`pg_dump` + uploads
  volume).

- **Unit/integration (Vitest):** permissions table, savePage/version rules,

- **E2E (Playwright):** sign up/log in, roles, spaces, nested pages, slash menu

## 12. Done checks by build stage

A stage is done when its checks pass in `npm run check` / `npm run e2e` **and**
someone on the team has done it by hand in a browser against the compose stack.

1. **Auth, spaces, nested pages** — three users sign up; first is admin; admin
   sets roles; a viewer cannot create or edit; a restricted space is invisible
   to non-members (UI and API return 404); pages nest three deep, reorder and
   move; breadcrumbs are right; session survives reload, logout ends it.
2. **Editor with slash commands and embeds** — `/` opens a filterable menu with
   every block in §3; image and file upload and render after reload; YouTube
   link becomes a player; a pasted URL can become a preview card; code block
   highlights; table can add/remove rows and columns; doc JSON has block ids and
   no base64; stale save returns 409 and is handled.
   Full check, split into items 2a (editor) and 2b (embeds):
   `docs/done-checks/02-editor.md`.
3. **Search and history** — a word typed in a page body is found within one
   save; a page in a restricted space never appears for a non-member; history
   lists versions with author and time; restoring an old version brings its
   content back and the newer versions are still listed.
   Full check, split into items 3a (search), 3b (history server) and 3c
   (history screen): `docs/done-checks/03-search-history.md`.
4. **AI** — with no key, no AI control is visible; with the stub, summarise
   returns text and ask returns an answer whose source links open pages the
   user can read; a page the asker cannot read is never cited.
   Full check, split into items 4a (provider switch), 4b (summarise), 4c (ask,
   server) and 4d (ask screen): `docs/done-checks/04-ai.md`.
5. **Look and finish** — light and dark both pass the contrast check; reduced
   motion is respected; `check-original` passes; `docker compose up` on a clean
   machine gives a working wiki.
6. **Page comments** — threads on the whole page or on one block, replies,
   edit, delete, resolve and reopen, all following the space role; a
   non-member gets 404. Full check, split into items 7a (server) and 7b
   (screen): `docs/done-checks/07-comments.md`. Design: §13.
7. **Page templates** — every "New page" opens a picker (Blank page, four
   built-ins, the space's own templates); "Save as template" on a page; a
   Templates tab in space settings to edit and delete; viewers see none of it;
   a non-member gets 404. Full check, split into items 8a (server) and 8b
   (screen): `docs/done-checks/08-templates.md`. Design: §14.
8. **Favourites and recently viewed** — anyone who can read a page can star
   it; Home shows the person's own Favourites and Recently viewed; lists are
   filtered by `visibleSpaceIds` when read, so lost access or a deleted page
   drops out at once; a non-member gets 404. Full check, split into items 9a
   (server) and 9b (screen): `docs/done-checks/09-favourites-recent.md`. Design: §15.
9. **Trash** — deleting a page or space moves it, with everything under it,
   to the trash with the same ids; editors restore from the space's Trash
   view, space admins delete for good or empty it, and items older than
   `TRASH_RETENTION_DAYS` go by themselves, file bytes included; nothing in
   the trash shows in search or AI answers. Full check, split into items 11a
   (server) and 11b (screen): `docs/done-checks/11-trash.md`. Design: §16.
10. **Task lists** — a task can have a person and a due date, set from the
   editor; My tasks lists a person's open tasks on pages they can read now,
   and ticking one there is a normal page save; trashed pages and lost access
   drop out at once. Full check, split into items 12a (server) and 12b
   (screen): `docs/done-checks/12-tasks.md`. Design: §17.
11. **Labels** — editors and admins add and remove named labels under a page's
   title; anyone who can read the page sees them; a per-space and a whole-wiki
   view list the labelled pages, and search takes `label:name`; a label or a
   page never shows to someone who cannot open it, and trashed pages drop out
   at once. Full check, split into items 13a (server) and 13b (screen):
   `docs/done-checks/13-labels.md`. Design: §18.

## 13. Comments

- **Own table, never in the page.** Comments live in `page_comments`
  (migration `0004_page_comments`): `id` (uuid, never reused), `page_id`
  (cascade on page delete), `parent_id` (one level of replies), `block_id`,
  `author_id`, `body` (plain text, 1–4,000 characters), `created_at`,
  `edited_at`, `resolved_at` / `resolved_by` (roots only), `deleted_at`
  (soft delete; the body is cleared). No comment action writes `pages`,
  `pages.version` or `page_versions`, so saving, history and restore never
  touch comments, and restoring an old version leaves them as they are.
- **Anchored to block ids, not positions.** A thread is on the whole page
  (`block_id` null) or on one top-level block, by that block's `attrs.id`
  (§3 rule 2). Typing above a block does not move its comments. If a save
  removes the block, the thread stays and shows "on a removed block". If a
  restore brings the block back, the thread is on it again.
- **Why it stays out of the Yjs document.** When co-editing comes, the Yjs
  document will hold page content only. Comments are not marks or nodes in it,
  so concurrent edits cannot break or duplicate them, and the comments table
  and routes need no change. Block ids already survive Yjs merges, so they stay
  valid anchors. The block markers on screen are an overlay drawn from the
  editor's block positions, not part of the document.
- **One permission path.** Every comment route goes through `requirePageRole`
  (§7): anyone who can read the page may comment and reply (a comment is not an
  edit); only the author may edit; the author or a space admin may delete;
  editors and up may resolve and reopen; someone who cannot read the page gets
  404.
- **Not yet:** live updates of other people's comments (the panel reloads when
  opened and after your own actions), mentions, notifications.

## 14. Templates

- **Own table, same document.** Space templates live in `page_templates`
  (migration `0005_page_templates`): `id`, `space_id` (cascade on space
  delete), `name` (1–80, unique in the space ignoring case), `description`
  (0–200), `doc`, `version`, `created_by` / `updated_by`, timestamps. `doc` is
  the same ProseMirror JSON as `pages.doc`, checked by the same `normalizeDoc`
  against the same editor schema and edited in the same block editor. There is
  no second format.
- **Built-ins live in code.** *Meeting notes*, *Project brief*, *How-to
  guide* and *Decision record* are in `apps/server/src/templates/builtin.ts`
  with fixed ids `builtin:<slug>`. Nothing is seeded, an upgrade can improve
  them, and nobody can edit or delete them (403).
- **A new page is a copy with fresh block ids.** Making a page from a template,
  and saving a page as a template, copies the doc and gives every top-level
  block a new id. The page does not point back to the template, so editing or
  deleting a template never changes pages already made from it, and no two
  pages share a block id (comment anchors and history stay per page). Pages are
  only ever made through `createPage`; no template route writes `pages` or
  `page_versions`.
- **One permission path.** Every template route goes through
  `requireSpaceByKey(…, 'editor')` (§7): editors and up use and manage
  templates, viewers get 403 and see no template control, someone who cannot
  see the space gets 404. Templates are not pages: they are not in the tree,
  search, history or AI.
- **Why co-editing needs no change.** Templates do not use `pages.ydoc_state`.
  When co-editing comes, a page made from a template is seeded from its copied
  JSON like any other new page. Templates themselves are edited by one person
  at a time with a `baseVersion` check (a stale save gets 409 and a Reload
  offer), so the table and routes stay as they are.
- **Not yet:** uploading a file straight into a template (files come in through
  "Save as template"; `attachments.page_id` stays NOT NULL), templates shared
  across spaces, template variables.

## 15. Favourites and recently viewed

- **Two small tables, nothing else.** Migration `0006_favourites_views` adds
  `page_favourites (user_id, page_id, created_at)` and
  `page_views (user_id, page_id, viewed_at)`. Each has the primary key
  `(user_id, page_id)`, cascades from `users` and `pages`, and one index on
  `(user_id, time desc)`. The rows hold a user id, a page id and a time,
  nothing more. Logic is in `apps/server/src/me/personal.ts`, routes in
  `apps/server/src/routes/personal.ts`.
- **Personal only.** Each person sees only their own lists, admins included.
  There are no counts or "starred by" lists anywhere.
- **Filtered when read, never cleaned up.** Starring and recording a view go
  through `requirePageRole(…, 'viewer')` (§7), so a page the person cannot read
  is 404. `GET /api/me/favourites` (newest first, up to 100) and
  `GET /api/me/recent` (newest first, up to 20) join `pages` and keep only
  pages where `deleted_at is null` and whose space is in
  `visibleSpaceIds(user)`. Losing access to a space, or a page being deleted,
  takes it off both lists at once. Getting access back brings it back. There
  is no second permission rule and no clean-up job.
- **A view is recorded on purpose.** `GET /api/pages/:id` stays read-only (it
  only gains `favourite: boolean`). The page screen calls
  `POST /api/pages/:id/viewed` once each time a page is opened (`PageView` is
  keyed by page id). Autosave, refetch and window focus never send it, so
  history, search, AI and the template picker cannot fill the list.
- **50-row cap.** A view is an upsert of `viewed_at` (one row per person and
  page). In the same transaction, any of that person's rows past their newest
  50 are deleted. Home shows 8 of each list.
- **Not content.** Favourites and views never change `pages.version`,
  `pages.updated_at` or `page_versions`, and they are not in search, AI or
  history.
- **Why co-editing needs no change.** These tables never touch the document
  or `pages.ydoc_state`. When co-editing comes, opening a page still sends one
  `viewed` call and the star is still one row per person, whoever else is
  editing the page.
- **Not yet:** favourite spaces, folders or ordering of favourites, a
  favourites section in the sidebar, view counts.

## 16. Trash

- **A state of the same rows, never a copy.** Migration `0007_trash` adds
  `pages.deleted_by`, `pages.trash_root_id` and `spaces.deleted_at`,
  `spaces.deleted_by`, plus the partial index `pages_trash_idx` on
  `(space_id, trash_root_id) where deleted_at is not null`. A page or space in
  the trash keeps its row and its id. Its sub-pages, history, comments, files,
  favourites and views are left as they are and are all there again on
  restore. Logic is in `apps/server/src/trash/trash.ts`, routes in
  `apps/server/src/routes/trash.ts`.
- **One trash item per delete.** Deleting a page sets `deleted_at`,
  `deleted_by` and `trash_root_id` (the deleted page's id) on it and every
  live page under it, in one statement. Restore and purge work on a whole
  item, found by `trash_root_id`. A sub-page deleted on its own earlier stays
  its own item. The migration back-fills older deletes so each one is one
  item.
- **Restore never leaves a live page under a trashed one.** The page goes
  back under its old parent if that parent is live, otherwise to the top of
  the space. It keeps its position key unless a live sibling has it.
- **Spaces.** A trashed space is hidden everywhere by `visibleSpaceIds` and
  the space loaders (§7), so its pages, files, search hits and AI sources go
  with it. Its key stays taken until it is purged. Trashed spaces are reached
  only by id, through `requireTrashedSpace`, which takes the role from
  `effectiveRole` like everything else.
- **Who.** Editors and up see a space's Trash and restore. Only space admins
  (and instance admins) purge and empty, and delete, restore or purge a
  space. Viewers get 403. People who cannot read the space get 404.
- **Purge rule.** By hand (one item, or empty the space's trash), or by time:
  `purgeExpired` removes items trashed `TRASH_RETENTION_DAYS` ago (default 30,
  `0` = never). It runs when the server starts and then hourly, inside the
  server process, and stops when the server closes. Purging deletes the rows
  (cascades remove sub-pages, history, comments, file rows, favourites and
  views) and then each file's bytes from `FileStorage`. Ids are never reused.
- **Kept out of reach.** Search and AI already skip deleted pages and pages
  under them. `readableAttachment` now also gives 404 for a file whose page
  is trashed or under a trashed page, which closes the old download gap.
  Opening a trashed page is 404 for everyone; for editors and up the 404
  carries the code `in_trash`, so the screen can link them to the Trash view.
  Viewers and non-members learn nothing.
- **Screens.** The space's Trash view is at `/s/:key/trash`
  (`apps/web/src/screens/Trash.tsx`), reached from a Trash link under the
  page tree that only editors and up see. Trashed spaces are listed under
  "Deleted spaces" on Home for their space admins and instance admins.
- **Why co-editing stays possible.** Trash, restore and purge never write
  `pages.doc`, `pages.version`, `pages.ydoc_state` or `page_versions`.
  A restored page is the same document with the same id and the same Yjs
  state. A co-editing session for a page can simply close when the page is
  trashed and open again on restore.
- **Not yet:** trash for single comments, templates or files; choosing where
  to restore to; restoring one sub-page out of a larger item.

## 17. Tasks

- **The page document is the truth.** A task is a `taskItem` node in
  `pages.doc` with the attrs `taskId`, `assignee` (a user id or null), `due`
  (`YYYY-MM-DD` or null, a calendar day with no time zone) and the old
  `checked`. They are part of the one editor schema
  (`packages/editor-schema/src/index.ts`) and round-trip through HTML as
  `data-task-id`, `data-assignee` and `data-due`. A bad date or a person id
  that is not a uuid makes the doc invalid (400).
- **Stable task ids.** Filled like block ids: the schema's `taskId` plugin in the browser
  gives a new task an id and a pasted or split copy a fresh one
  (`keepOnSplit: false`); `parseDoc` on the server fills any task with no id
  or a repeated one, nested tasks included. Ids are unique within a page.
- **`page_tasks` is an index, rebuilt on save.** Migration `0008_tasks` adds
  `page_tasks`, keyed by `(page_id, task_id)`, with the partial index
  `page_tasks_open_idx` on `(assignee_id, due) where checked = false`.
  `createPage` and `savePage` replace a page's rows from `docTasks(doc)` in the
  same transaction as the page row (`replaceTasks` in `pages/pages.ts`), the
  way `doc_text` is kept. Nothing else writes it. So a history restore, a
  template or an old doc keep it right with no extra code, and trash leaves it
  alone (purge removes it by cascade).
- **My tasks is filtered when read.** `GET /api/me/tasks` lists open tasks
  given to the person, on live pages, in spaces from `visibleSpaceIds`, with
  `canTick` from `effectiveRole` (`apps/server/src/tasks/tasks.ts`). Losing
  access or trashing a page hides a task at once, and a restore brings it
  back. The picker (`GET /api/spaces/:key/people`) lists active people who
  can read the space; a save naming someone else is not refused, the task
  just never shows for them, and the editor shows them as "No access". A
  person id that is not anyone on this wiki is kept in the doc as sent, but
  its `page_tasks` row gets `assignee_id` null (one `users` lookup per save,
  same transaction), so the save never fails on it.
- **A tick is a page save.** `PATCH /api/pages/:id/tasks/:taskId` reads the
  doc and version, flips `checked` on that one node and saves through
  `savePage` with that version as the base: a normal version in history by
  the person who ticked, page, block and task ids unchanged. A save in between
  (409) is retried once, then shown as "The page just changed, try again".
  Anyone with the page open meets the usual save-conflict note.
- **Screens.** Chips and the Assign / Due date controls are a node view on
  `taskItem` (`apps/web/src/editor/tasks.tsx`), also on Alt+Shift+A and
  Alt+Shift+D. My tasks is `/tasks` (`apps/web/src/screens/MyTasks.tsx`),
  grouped Overdue, Today, Coming up, No date, with tick, fade and Undo.
- **Why co-editing stays possible.** Everything about a task lives in node
  attrs, which Yjs keeps as they are, and the index is rebuilt from whatever
  doc is saved, so a co-editing server that saves through `savePage` keeps My
  tasks right with no change. A tick is an ordinary edit of one attr; under
  co-editing it can become a small Yjs update to that node instead of a whole
  save, with the same ids.
- **Not yet:** notifications or email, @mentions, more than one person per
  task, reminders, repeating tasks, a list of done tasks, a team task board.

## 18. Labels

- **Beside the page, not inside it.** A label is a named tag kept in its own
  two tables (migration `0009_labels`), never in `pages.doc`. `labels` holds
  one row per name with a uuid that never changes; `page_labels` links a page
  to a label, keyed by `(page_id, label_id)`, with the index
  `page_labels_label_idx` on `label_id`. There is no space column: the space
  is read from `pages`, so a page move needs no extra code. A `labels` row
  stays when no page uses it any more, so the same name keeps the same id.
- **One name rule.** `normaliseLabel` in `packages/shared/src/index.ts`, used
  by the server and the screen: trim, lower-case, spaces become `-`, only
  letters (any language), digits, `-` and `_`, 1 to 40 characters. At most 20
  labels per page; adds to one page are serialised with an advisory lock so
  two at once cannot pass the limit.
- **Add and remove are set operations that never touch the page.**
  `POST /api/pages/:id/labels` and `DELETE /api/pages/:id/labels/:labelId`
  (editor and up, `apps/server/src/labels/labels.ts`) only write `labels` and
  `page_labels`. They never write `pages` or `page_versions` and never call
  `savePage`, so `pages.doc`, `pages.version` and `pages.updated_at` stay as
  they are. Adding a label the page has, or removing one it lacks, is a 200
  with no change. Someone with the page open never gets a save conflict
  because it was labelled, and a history restore keeps today's labels
  (labels are not part of a version).
- **Filtered when read, one permission path.** The page's own label routes go
  through `requirePageRole` (a page you cannot read is 404, a viewer gets 403
  on add and remove). Every other read (`GET /api/pages/:id`, suggestions
  `GET /api/labels`, the views `GET /api/labels/:name/pages` and
  `GET /api/spaces/:key/labels/:name/pages`, and search) keeps only live pages
  (`pages.deleted_at` is null, which trash sets on every page under a trashed
  one) in spaces from `visibleSpaceIds`. So a label used only in a space you
  cannot read is never suggested or counted, and its view looks the same as
  a name never used. Trash, restore and the timed purge leave `page_labels`
  alone: a trashed page's labels are hidden with it and come back with it;
  purge removes them by cascade.
- **Search.** The label filter is part of the one `searchPages` statement
  (`apps/server/src/search/search.ts`): `label=` (repeatable) and `label:name`
  words in the box, every label required; with no other words it lists the
  labelled pages newest change first. Label names are not added to the
  full-text column.
- **Screens.** Chips and the Add label control under the page title
  (`apps/web/src/labels/PageLabels.tsx`, read-only for viewers); the views at
  `/s/:key/labels/:name` and `/labels/:name`
  (`apps/web/src/labels/LabelScreens.tsx`); label chips on `/search`. Styles
  in `styles/labels.css`, tokens only.
- **Why co-editing stays possible.** Labels sit outside the document and its
  version, so a co-editing server that takes over `pages.doc` needs no change
  for them. Set adds and removes merge in any order with no base version, the
  same shape a Yjs map of label ids would have if labels ever move into the
  shared document, and the ids stay the same either way.
- **Not yet:** label colours, renaming or merging labels, an admin screen for
  labels, labels on spaces, templates or comments, labels in page history.

## 19. Mentions, following and notifications

- **A mention is a person id in the document, like a task assignee.** It is
  an inline atom node `mention` in the one editor schema with `userId` (a
  uuid, required) and `label` (the name when mentioned, a fallback only). It
  round-trips through HTML as `span[data-mention][data-user-id]`; a non-uuid
  id makes the doc a 400. `docMentions(doc)` reads the ids out. In plain text
  (search, AI) it reads `@label`; the screen shows the person's current name,
  or "No access" / "Unknown person". Naming someone who cannot read the space
  is never refused; they are simply never told. `@` suggestions use the same
  `GET /api/spaces/:key/people` as the task picker.
- **Notifications are written in the transaction of the thing they are
  about** (`apps/server/src/notifications/notifications.ts`, migration
  `0010_mentions_notifications`): `createPage` and `savePage` tell each person
  newly mentioned (old mentions read under a row lock), `savePage` tells every
  follower about the edit, and `createComment` tells every follower about the
  comment. So a notification is never lost or doubled. Never the actor, never
  a disabled person, and only people who can read the space at that moment.
- **Edits fold.** A partial unique index on unread edit notifications per
  person and page makes a further save an upsert: newest editor, time and a
  count of saves on the one row ("edited … (3 changes)"). Once read, the next
  save starts a new row.
- **Filtered when read, one filter.** The list and the unread count both use
  `visibleTo(user)`: the page is live and in a space from `visibleSpaceIds`,
  and a comment notification's comment is not deleted. Trash or losing access
  hides them at once; restore or getting access back brings them back; purge
  removes them by cascade. There is no clean-up job.
- **Following.** `page_follows` keyed by `(user_id, page_id)`. You follow on
  create and on commenting (insert if missing, so a later unfollow sticks);
  anyone who can read a page can follow it, through `requirePageRole`, so
  anyone else gets 404.
- **Screens.** The `@` list and chips (`apps/web/src/editor/mentions.tsx`),
  the Follow button on the page, and the bell with its count and panel
  (`apps/web/src/notifications/`). The bell asks for the count on open, every
  60 s while visible, on window focus and after opening the list. A comment
  notification opens the comments panel on that comment (`?comment=`).
- **Why co-editing stays possible.** A mention is an atom node with attrs,
  which Yjs keeps as they are, and the "who is newly mentioned" diff runs
  inside `savePage`, so a co-editing server that saves through `savePage`
  tells the same people with no change. Follows and notifications hold only
  ids and a time and sit in their own tables; they never write `pages.doc`,
  `pages.version`, `pages.updated_at` or `page_versions`, so following or
  being told never causes a save conflict.
- **Not yet:** email or push, live push of the count, mentions in comments,
  mentioning a group, following a space or a page tree, per-kind settings.

## 20. Export

- **Read-only, from the saved document, through the one schema.** `GET
  /api/pages/:id/export?format=md|pdf&children=0|1` reads `pages.doc` through
  `parseDoc` and turns it into Markdown (`apps/server/src/export/markdown.ts`,
  one `.md`, or a `.zip` made with `fflate` when there are files or sub-pages)
  or a PDF (`export/pdf.ts`, `pdfmake` with its bundled Roboto fonts and the
  built-in Courier, always the calm light look). It is built in memory and
  sent in one answer: no job, no file left on disk. No export code writes any
  table and none calls `savePage`, so `pages.version`, `pages.updated_at` and
  `page_versions` never change (the server test compares them before and
  after every export).
- **One permission path.** `planExport` in `export/collect.ts` starts with
  `requirePageRole(viewer)`, so anyone who can read the page can export it,
  someone who can't gets 404 and signed out gets 401, the same as opening the
  page. The sub-page walk stays inside that space and only goes into children
  with `deleted_at is null`, so a trashed page and everything under it is left
  out with no trace; a trashed page, branch or space is itself a 404.
- **Files only through `readableAttachment`.** Every image, file and uploaded
  video in the document is checked for the exporting person; one that fails
  becomes a plain "… not available" line and its bytes are never read. In the
  zip they sit in `attachments/<id>-<clean name>` behind relative links;
  links to pages in the same export point to their `.md`, other wiki links to
  the full address (which still needs sign-in).
- **No outside fetch.** The server never fetches anything while exporting:
  pdfmake's URL policy refuses every address and its local policy allows only
  its own fonts, and a link preview's picture or a video address stays a link.
- **Limits, checked before anything is built.** At most 200 pages and 100 MB
  of files (`EXPORT_MAX_PAGES`, `EXPORT_MAX_FILE_BYTES` in `packages/shared`).
  The page count is checked straight after the walk and the file total from
  the stored sizes, before any document is parsed or file read; above either
  it is a 413 with a plain message. `check=1` runs the same walk and limits
  and answers 204 with no file, so the screen can show a 413 as a quiet note
  before the browser starts a plain `<a download>` with its sign-in cookie.
- **Screen.** The Export button and menu next to Follow and the star
  (`apps/web/src/export/ExportMenu.tsx`): "This page only" / "This page and
  its N sub-pages" when `childCount` (on `GET /api/pages/:id`) is above 0,
  then Markdown and PDF; full keyboard use and screen-reader labels; tokens
  only and the shared reduced-motion rule.
- **Why co-editing can still be added without a rewrite.** Export only reads
  what `savePage` stored, through the one schema. A co-editing server still
  saves through `savePage` into `pages.doc`, so export reads the same thing
  with no change, and because export writes nothing it can never clash with
  anyone editing.
- **Not yet:** exporting a whole space, Word or HTML, any import, comments or
  history in the export, scheduled or emailed exports, fonts for scripts
  Roboto does not cover (they show as blank boxes, noted in INSTALL.md).
